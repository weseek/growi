## 2026-09-11 Amendment round 8: highlight lost after a minor edit + return-to-View (no reload)

The user reported: add an inline comment → open the editor → make a small edit → save → return to View (no reload) → the edited area's highlight is gone; a full browser reload restores it for a modest edit. Out of this spec's own boundary (a functional correctness bug in anchor resolution, not a visual-styling concern) but investigated and fixed in the same session per this spec's established practice for user-reported bugs found while using the shipped feature.

Root cause: `observeContainerSettle` (`AnchorResolver/use-container-settle.ts`) — the mechanism `useAnchorResolver` relies on to know when to re-match a comment's saved quote against the current DOM — observed the page-body container with `{ childList: true, subtree: true, attributes: true, attributeFilter: [...] }`, omitting `characterData: true`. A same-length in-place text correction (fixing a typo, editing a word) makes React update an existing Text node's `data` directly rather than adding/removing any element — a `characterData`-type `MutationRecord`, not a `childList` one — so the observer never fired, `useAnchorResolver` never re-ran, and the highlight stayed anchored to whatever it last resolved (stale or empty). A full page reload sidesteps this entirely: `useAnchorResolver` always resolves once, synchronously, at mount (`observeContainerSettle`'s `fireIfSettled()` call before any observation even starts), independent of this observer gap — which is why a reload "fixes" it while returning from the editor doesn't.

- Verified via a live-page diagnostic (a throwaway Playwright test installing its own `characterData`-enabled `MutationObserver` on `.wiki` and logging record types across a real editor-save-return round trip): the real ReactMarkdown-rendered page genuinely emits a standalone `characterData` record for this class of edit — not merely a synthetic DOM API argument. Also confirmed with a minimal happy-dom reproduction that a `childList`/`attributes`-only observer provably does not fire for a text-node-only mutation (spec-conformant behavior, not a test-environment quirk).
- Fix: added `characterData: true` to the single `observer.observe(...)` call. One line; no other logic needed to change — `scheduleSettle`/`fireIfSettled` already re-evaluate the container generically on any observed change.
- Added a regression test to `use-container-settle.spec.tsx` (mutation-checked: reverted the fix via a tagged `git stash`, confirmed the new test goes RED, restored and confirmed GREEN, then dropped the stash entry) asserting `onSettle` fires when an existing text node's `data` changes in place with no element added or removed.
