# Requirements Document

## Project Description (Input)
管理画面のセキュリティ設定から、scrypt への移行が済んだユーザーに限って、MongoDB の users コレクションに残る旧 SHA-256 パスワードを削除する機能。

- **誰が困っているか**: GROWI.cloud など、サーバーのシェルに入れない環境の GROWI 管理者。
- **現状**: password-hash-upgrade で、旧 SHA-256 ハッシュを削除する cleanup 用 migration スクリプトと、移行状況を確認する status スクリプトを用意した。しかし、どちらもサーバー上で実行する必要があるため、シェルに入れない管理者は旧ハッシュを削除できず、移行がどこまで進んだかも確認できない。
- **どう変えるか**:
  - 管理画面のセキュリティ設定に、パスワード形式ごとのユーザー数（移行状況）を表示する。
  - 同じ画面から、scrypt への移行が済んだユーザーの旧 SHA-256 パスワード（`password` フィールド）を削除できるようにする。
  - 既存の cleanup スクリプトは残し、削除ロジックを共有する。
  - 未移行（旧ハッシュしか持たない）の ACTIVE ユーザーが残っていても処理を中止しない。移行済みのユーザーだけを対象に削除し、未移行のユーザーには手を付けない。この点で、未移行の ACTIVE ユーザーがいると中止する既存スクリプトとは挙動が異なる。

## Introduction
password-hash-upgrade により、ローカル認証のパスワードは旧形式（SHA-256 + PASSWORD_SEED）から新形式（scrypt）へ、ログイン時に段階的に移行される。移行の途中では、ユーザーが旧形式と新形式の両方のパスワードを持つことがある。旧形式のパスワードはログインには使われなくなっているが、弱いハッシュのまま残り続ける。

この機能は、サーバーのシェルに入れない管理者でも、管理画面のセキュリティ設定から移行状況を確認し、移行済みユーザーの旧形式パスワードを削除できるようにする。

本書で使う用語:
- **旧形式パスワード**: SHA-256 + PASSWORD_SEED で保存されたパスワード
- **新形式パスワード**: scrypt で保存されたパスワード
- **移行済みユーザー**: 旧形式と新形式の両方を持つユーザー。この機能の削除対象
- **未移行ユーザー**: 旧形式だけを持つユーザー

## Boundary Context
- **In scope**:
  - 管理画面のセキュリティ設定での移行状況（パスワード形式ごとのユーザー数）の表示
  - 移行済みユーザーの旧形式パスワードの一括削除（確認ダイアログと監査ログを含む）
- **Out of scope**:
  - 未移行ユーザーへの移行の強制、ログインの催促、パスワードリセットメールの送信
  - PASSWORD_SEED 環境変数の削除・変更、およびその案内
  - ダウングレード準備・再アップグレード準備の画面化（従来どおりスクリプトで行う）
  - 既存の status / cleanup スクリプトの挙動変更
- **Adjacent expectations**:
  - 新形式パスワードを持つユーザーのログイン検証は、すでに新形式だけで行われている（password-hash-upgrade の Requirement 2）。そのため、旧形式パスワードを削除しても、現行バージョンでのログインには影響しない。
  - パスワードの変更・リセットでは、すでに旧形式パスワードが除去されている。この機能はその挙動に依存するだけで、変更はしない。
  - 外部認証だけを使うユーザーなど、パスワード未設定のユーザーはこの機能の影響を受けない。

## Requirements

### Requirement 1: 移行状況の表示
**Objective:** As a GROWI 管理者, I want パスワード形式ごとのユーザー数を管理画面で確認したい, so that シェルに入らなくても、移行の進み具合と削除できる件数を判断できる

#### Acceptance Criteria
1. When 管理者がセキュリティ設定画面を開いたとき, the GROWI 管理画面 shall 「新形式のみ」「両形式（移行済み）」「旧形式のみ（未移行）」「パスワード未設定」の 4 区分のユーザー数を表示する。
2. The GROWI 管理画面 shall 「旧形式のみ（未移行）」の件数を、ACTIVE ユーザーと ACTIVE 以外のユーザーの内訳に分けて表示する。
3. The GROWI 管理画面 shall 「両形式（移行済み）」の件数を、旧形式パスワード削除の対象件数として示す。
4. When 旧形式パスワードの削除が完了したとき, the GROWI 管理画面 shall 画面を再読み込みしなくても、表示中の件数を削除後の最新の値に更新する。
5. If 件数の取得に失敗したとき, then the GROWI 管理画面 shall エラーメッセージを表示し、削除の実行を受け付けない。

### Requirement 2: 移行済みユーザーの旧形式パスワード削除
**Objective:** As a GROWI 管理者, I want 移行済みユーザーの旧形式パスワードを画面から削除したい, so that 弱いハッシュをデータベースに残さずに済む

#### Acceptance Criteria
1. When 管理者が削除を実行し、確認ダイアログで実行を確定したとき, the GROWI サーバー shall 移行済みのすべてのユーザーから、アカウントのステータスにかかわらず旧形式パスワードを削除する。
2. The GROWI サーバー shall 新形式のみのユーザー、未移行ユーザー、パスワード未設定のユーザーの保存データを変更しない。
3. While 未移行の ACTIVE ユーザーが 1 人以上いるとき, the GROWI サーバー shall 削除を中止せず、移行済みユーザーだけを対象に削除を行う。
4. When 削除が完了したとき, the GROWI 管理画面 shall 旧形式パスワードを削除したユーザー数を成功メッセージとして表示する。
5. While 移行済みユーザーが 0 人のとき, the GROWI 管理画面 shall 削除の実行操作を無効にする。
6. When 削除の対象がいない状態で削除が要求されたとき, the GROWI サーバー shall どのユーザーの保存データも変更せず、削除件数 0 として正常に応答する。
7. If 削除の途中でエラーが発生したとき, then the GROWI 管理画面 shall エラーメッセージを表示し、成功メッセージを表示しない。
8. When 旧形式パスワードを削除されたユーザーが、現行バージョンで新形式パスワードに対応する正しいパスワードを入力してログインしたとき, the GROWI 認証システム shall 削除前と同じようにログインを許可する。

### Requirement 3: 実行前の確認と影響の警告
**Objective:** As a GROWI 管理者, I want 削除を実行する前に、対象件数と取り消せない影響を確認したい, so that ダウングレードの予定などを踏まえて、実行してよいか判断できる

#### Acceptance Criteria
1. When 管理者が削除の実行操作を行ったとき, the GROWI 管理画面 shall 削除を始める前に確認ダイアログを表示する。
2. The GROWI 管理画面 shall 確認ダイアログに、削除対象のユーザー数と、削除は取り消せないことを表示する。
3. The GROWI 管理画面 shall 確認ダイアログに、次の警告を表示する。削除後に新形式パスワードに対応しない旧バージョンへダウングレードすると、対象ユーザーはログインできなくなる。ACTIVE ユーザーはパスワードリセットで復旧できるが、ACTIVE 以外のユーザーは管理者が個別に対応する必要がある。
4. When 管理者が確認ダイアログでキャンセルしたとき, the GROWI 管理画面 shall 削除を行わずにダイアログを閉じる。

### Requirement 4: 権限と監査
**Objective:** As a GROWI 管理者, I want 削除操作を管理者だけに限定し、記録に残したい, so that 誰がいつ実行したかを後から追跡できる

#### Acceptance Criteria
1. The GROWI サーバー shall 移行状況の取得と旧形式パスワードの削除を、管理者権限を持つユーザーだけに許可する。
2. If 管理者権限を持たないユーザーが移行状況の取得、または削除を要求したとき, then the GROWI サーバー shall 要求を拒否し、データを返さず、保存データを変更しない。
3. Where 監査ログが有効で、他の管理者操作と同じ記録範囲の設定によってこの操作が記録対象に含まれるとき, the GROWI サーバー shall 旧形式パスワードの削除を実行した管理者と操作の種類を監査ログに記録する。
4. The GROWI 管理画面 shall パスワードやハッシュの値そのものを表示しない。表示するのはユーザー数だけとする。
5. When 旧形式パスワードの削除が実行されたとき, the GROWI サーバー shall 監査ログの設定にかかわらず、実行した管理者と削除件数をサーバーログに出力する。

### Requirement 5: 既存スクリプトとの併存
**Objective:** As a GROWI 管理者（シェルに入れる環境）, I want 既存の cleanup スクリプトを従来どおり使い続けたい, so that 運用手順を変えずに済む

#### Acceptance Criteria
1. The GROWI 移行システム shall 既存の cleanup スクリプトと status スクリプトを、従来と同じ挙動のまま提供し続ける。cleanup スクリプトが未移行の ACTIVE ユーザーがいると中止する挙動も含む。
2. The GROWI サーバー shall 管理画面からの削除で、cleanup スクリプトと同じ基準（移行済みユーザー）で対象ユーザーを選ぶ。
3. The GROWI 管理画面 shall 移行状況の 4 区分を、status スクリプトが報告する区分と同じ定義で数える。

### Requirement 6: 表示文言の多言語対応
**Objective:** As a 日本語以外の UI 言語を使う GROWI 管理者, I want この機能の表示を自分の UI 言語で読みたい, so that 取り消せない操作の警告を正しく理解できる

#### Acceptance Criteria
1. The GROWI 管理画面 shall この機能で追加する表示文言（見出し、件数の区分名、ボタン、確認ダイアログ、警告、成功・エラーメッセージ）を、GROWI が提供するすべての UI 言語で表示する。
